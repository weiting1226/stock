# 美股監控系統 — 每日自動爬蟲 + 儀表板

兩個獨立模組，各自每天自動更新一次，共用同一組靜態網頁儀表板（GitHub Pages）：

| 模組 | 內容 | 頁面 | 排程 |
|---|---|---|---|
| **模組一** | 市場流動性雙軌監控系統 v3.0（總體擇時） | `docs/index.html` | 平日 22:30 UTC |
| **模組二** | 分析師估值與市價差異比較（個股選股） | `docs/valuation.html` | 週二至週六 23:10 UTC |

# 模組一：市場流動性雙軌監控系統 v3.0

依據《市場流動性雙軌監控與交易策略系統 v3.0》文件，自動抓取文件「一、資料抓取規範」
列出的權威資料源、依「二、軌道一計分」與「三、三道閘門」規則計算分數與部位建議，
每天執行一次，並輸出成靜態網頁儀表板（GitHub Pages）供查詢。

## 架構

```
liquidity_monitor/        資料抓取 + 計分引擎（純 Python，可離線單元測試）
  config.py                資料源代碼、發布時滯、權重、門檻表（抄錄自 v3.0 文件）
  sources/                 各資料源的抓取器（FRED / Yahoo Finance / FINRA / 維基百科 / Fed）
  timeseries.py            時滯位移、交易日對齊、年增率/區間變化等純函式工具
  scoring.py                18項子項計分、類別平均、綜合分數、燈號、結構性警示
  gates.py                  Gate A/B/C 判定 + 軌道二簡化版每日近似訊號
  pipeline.py                串接以上模組，產出當日完整報告(dict)
  storage.py                 把報告寫進 docs/data/（給前端儀表板讀取）
scripts/run_daily.py       每日排程進入點（CLI）
.github/workflows/daily-scrape.yml   GitHub Actions 排程（平日 22:30 UTC）
docs/                        GitHub Pages 網站根目錄（純前端，讀取 docs/data/ 的 JSON/CSV）
tests/                        pytest，全部使用合成/mock資料，不需要網路連線
```

## 快速開始

```bash
pip install -r requirements.txt
python3 scripts/run_daily.py -v          # 抓今天的資料，寫到 docs/data/
python3 -m pytest tests/ -v               # 跑離線測試（純函式 + mock網路的整合測試）
```

### 開啟 GitHub Pages（一次性手動設定，本專案的程式碼無法自動開啟）

1. Repo → Settings → Pages
2. Source 選「Deploy from a branch」，Branch 選 `main` / 資料夾選 `/docs`
3. 存好後幾分鐘網址會是 `https://<你的帳號>.github.io/<repo>/`

### 每日自動更新的注意事項

GitHub Actions 的 `schedule` (cron) **只會在預設分支 (通常是 main) 上生效**。
這個工作流程檔案目前是跟著這次的 PR 一起開發在功能分支上，**merge 進 main 之後
排程才會真的開始每天執行**；在那之前可以用 Actions 頁籤手動點
「Run workflow」(workflow_dispatch) 測試。

## 資料真實性 / 誠實原則（比照文件第285-292行）

- 抓不到、解析失敗、或資料源本身不存在（NDX前瞻本益比），
  一律標記「暫缺」，**絕不用其他數字頂替**，也不會讓整個計分流程失敗——該子項在
  「類別平均分」中被排除，該類別缺一整類時權重按比例分攤給其餘類別（`scoring.composite_score`）。
- 每一項在 `docs/data/latest.json` 都附有信心等級（高/中/低/暫缺）與資料日期，
  對應儀表板「當日18項數據查證清單」。
- Gate B 的「過去10年百分位」若歷史資料不足會改用文件表格的2026年參考門檻，並在
  UI 上標註 `approx: true`（近似值），不會偷換成固定門檻假裝是真百分位。
- 30Y殖利率60日動能、Gate A「NDX在200日線之上但均線未明確上彎」這類文件只給
  質化描述、沒給精確數字門檻的地方，程式碼裡都用中文註解明確標出「本專案自訂假設」，
  供人工複核調整。

## 已知限制

1. **軌道二（即時應變層）本質是盤中事件監控**，每日批次爬蟲無法取得真正盤中資料。
   儀表板「軌道二」區塊是用「日收盤對日收盤」變化回推的簡化近似（僅第一層四項訊號），
   非真正熔斷判定，UI 上已明確標註不得作為加碼依據。第二、三層（SOFR盤中異常、
   熔斷紀錄、亞股/原油盤中異常）完全不在本專案範圍內。
2. **FOMC異議票偵測**是規則式文字比對（搜尋"voting against"），非語意理解；聯準會
   新聞稿改版格式時會直接拋出錯誤而非給錯誤答案。
3. **NDX 200日線廣度**用的是「目前」NASDAQ-100成分股清單回推過去價格，屬於
   look-back bias（成分股是會變動的），不是嚴格的時點正確計算。
4. 本專案開發環境的沙盒沒有對外網路權限（`fred.stlouisfed.org` / `finance.yahoo.com` /
   `finra.org` / `federalreserve.gov` 皆連不到），所有抓取邏輯是用合成資料的整合測試
   （`tests/test_pipeline.py`）驗證流程正確性，**尚未對真實網站的即時回應格式做過驗證**。
   GitHub Actions runner 有一般網路權限，理論上可以正常執行，但第一次實際跑通後
   請人工檢查 `docs/data/latest.json`，特別留意 FINRA 融資餘額與 FOMC 新聞稿解析
   （這兩個資料源版面最容易改版）。若解析失敗，函式會拋出清楚的錯誤訊息而不是
   回傳錯誤數字，可用 `--margin-override-csv` 或 `manual_overrides.json` 人工備援。

|---|---|---|
| `fomc_decision` | 60 天 | 每次 FOMC 會後（一年8次，平均間隔約46天）|
| `fedwatch_path` | 14 天 | 每週 |
| `etf_fund_flow` | 14 天 | 每週 |
| `ndx_fwd_pe` | 45 天 | 每月 |

### ⑥ FOMC 決議偏向（AI 摘要與分類）

規格第135行：**降息無異議 +2 ／降息有異議 +1 ／持平無異議 0 ／持平但有升息異議 −1 ／升息 −2**。

原本的判斷是 `re.search("voting against")`——只知道**有沒有人投反對票**，
不知道**反對的方向**。但規格那一列寫的是「持平但有**升息**異議」：反對者主張
升息才是鷹派訊號；若他主張的是降息，那反而偏鴿。同一個正則把兩者算成同一件事，
**等於把一個訊號和它的反面混為一談**。

改由模型讀完整聲明，輸出結構化結果（升／降／持平、異議人數與方向、中文摘要），
摘要會顯示在儀表板的備註欄。

#### 三道防線確保它不會亂編

| 防線 | 作用 |
|---|---|
| **輸出限定 JSON schema** | `decision`／`dissent_direction` 不在允許值內就當作失敗，不做寬鬆解析 |
| **要求引用原文** | 異議判定必須附上聲明中的原句，且該句要真的逐字出現在全文裡，否則視為幻覺並丟棄該判定 |
| **硬資料勝過模型** | 升降息幅度以 FRED `DFEDTARU` 的實際目標區間為準；模型只在「異議方向」與「摘要」上有裁量權 |

第二道是最有效的：模型可以編出一段看起來合理的敘述，但編不出一段**剛好逐字
出現在原文**的句子。引文比對容許空白與引號樣式的差異（原文經過去標籤處理），
但不容許改寫。

模型與 FRED 不一致時採用 FRED 並把矛盾記進備註——那通常代表聲明抓錯了場次，
值得人看一眼。

#### 設定

Repo → Settings → Secrets and variables → Actions → 新增 `ANTHROPIC_API_KEY`。

**沒設定不會中斷**：自動退回原本的字串比對，並在備註標明「無法分辨異議方向」，
信心從「高」降為「中」。

### ⑥ 市場隱含 12 個月路徑（AI 判讀 FedWatch）

規格第136行：**降息≥2碼 +2 ／降息1碼 +1 ／持平 0 ／升息1碼 −1 ／升息≥2碼 −2**。

FedWatch 的機率表是「各次會議 × 各目標區間」的二維表，要讀出「12 個月後的隱含
利率」需要理解表格語意——這正是模型比正則式解析有優勢的地方。

#### 紅線：模型只讀畫面上的數字，不回憶市場預期

**頁面抓不到就不呼叫模型。** 讓它憑記憶說「市場預期降兩碼」是編造，不是解讀。
另有三道檢查：

| 檢查 | 擋掉什麼 |
|---|---|
| `found: false` 要當失敗 | 機率表由 JavaScript 載入時頁面只有框架，此時回報 0（持平）會是假訊號 |
| 佐證片段須逐字出現在頁面 | 模型自己編的數字 |
| 隱含利率須落在 0–10% | 把「機率」欄（62.4%）當成「利率」讀 |

抓到的頁面若短於 500 字元也直接判定不可用——那種只有框架的頁面正是幻覺的溫床。

#### 計分要先歸到「碼」

規格是以碼（25bp）為單位描述的，但隱含路徑是連續值。−37bp 這種數字必須先
四捨五入到最接近的碼，才有對應的等級（−37bp → 降息1碼 → +1；−38bp → 降息2碼 → +2）。

#### 備援：一年期公債近似

FedWatch 抓不到時，退回「1 年期公債殖利率 − 目前目標區間中點」。
**這是近似值，不是 FedWatch**：一年期殖利率約等於未來一年政策利率的平均預期
**加上期限溢酬**，後者無法從這裡拆出來。因此信心只給「低」，並在備註寫明是近似
——不能讓它在畫面上看起來跟真的市場隱含機率一樣。

而且**近似法最多只說到 ±1**。期限溢酬約 10–20bp，與「一碼」的 25bp 是同一個
數量級，它的偏差大到足以跨越一個等級。2026-08 實測正好踩到：

```
1年期公債 4.06% vs 目標中點 3.625% = +43.5bp -> 四捨五入 2 碼 -> −2
但扣掉任何合理的期限溢酬（10/15/20bp）後      -> 都只剩 1 碼 -> −1
```

近似法分得出方向與「有沒有明顯定價」，分不出 1 碼還是 2 碼，那就不要說到 ±2
——與資金流歷史不足時只判方向是同一個原則：少說一級。真的讀到 FedWatch
機率表時精度足夠，不受此限。

### ⑤ 股票型 ETF 資金流（自行計算申贖流量）

**ETF.com 從 GitHub Actions 存取時三個位址全部回 403**（Cloudflare 擋資料中心 IP，
2026-08 實測）。繞過網站刻意設下的存取控制既不恰當、也必然脆弱，因此改為自行計算。

#### 為什麼這是定義而不是代理指標

ETF 的流通股數**只會因為授權參與者的申購（creation）與贖回（redemption）而變動**
——買賣既有股份不會改變股數。因此「Δ流通股數 × 價格」就是流入／流出該檔 ETF 的
實際金額本身。

樣本為規模最大的 16 檔美國股票型 ETF（SPY／IVV／VOO／VTI／QQQ／IWM…）。不求窮盡
全市場：計分本來就是拿它跟自己的歷史比，**樣本一致比涵蓋完整更重要**。

| 方法 | 何時採用 | 精確度 |
|---|---|---|
| Δ流通股數 × 價格 | 半數以上的 ETF 股數通過可信度檢查 | 精確——這就是申贖金額 |
| AUM − 前日AUM × (1+報酬率) | 否則 | 估計——把市值變動中「漲跌造成的部分」扣掉 |

兩種基礎**不混用**：混了之後這個序列跟自己的歷史就不可比，而計分完全依賴「跟自己比」。

#### 實測：Yahoo 對 ETF 的 sharesOutstanding 不可靠

對 ETF 而言「流通股數 × 價格」依定義就等於淨資產。拿這個恆等式去驗，
2026-08-09 實測 16 檔**只有 4 檔對得起來**：

| 通過 | 比值 | | 不通過 | 比值 |
|---|---|---|---|---|
| DIA | 0.97 | | VUG | **0.06**（差 16 倍）|
| IWD | 0.96 | | VTI | **0.12** |
| IWM | 1.05 | | IJH | **0.16** |
| SPY | 0.89 | | QQQ／RSP／IVV… | 0.29–0.76 |

另有 SPLG、VOO 根本沒有股數欄位。**少了這道檢查，程式會照樣拿這些數字去算
差額——算出來的「資金流」看起來完全正常，實際上毫無意義。**

而且它**時有時無**：同一天稍晚再抓一次，DIA 與 IWD 的股數就變成空值，
通過檢查的只剩 IWM 與 SPY（合計僅占樣本淨資產的 11.7%，其中 SPY 就占九成）。

這同時排除了另一個看似合理的選項——「只取股數可信的那幾檔」：那樣的樣本
會由 SPY 主導，而 SPY 的申贖大量來自機構避險部位，不能代表整體股票型資金流；
何況樣本組成本身還會逐日飄移。因此實務上走的是淨資產法（涵蓋全部 16 檔）；
若日後資料源修正，會自動切回精確的股數法。

#### 為什麼計分用「佔樣本淨資產的比例」而非絕對金額

樣本組成一有增減（某檔當天資料缺漏、或清單調整），絕對金額就會跟著跳動，
但計分完全依賴「跟自己的歷史比」——那個跳動會被誤讀成資金流變化。
改用佔樣本淨資產的比例就沒有這個問題：它是尺度無關的量。
`net_flow_musd` 仍會顯示在備註裡供人判讀。

#### 三個必要的防呆

- **分割不是資金流**：ETF 分割會讓股數瞬間倍增或減半。單日股數變動超過 30% 一律
  略過並記錄原因——不擋掉的話會產生一筆虛假的巨額流入，而且看起來完全合理。
- **跨日要攤平**：長假或排程中斷後那一筆若不除以間隔天數，會被當成暴量單日訊號。
  間隔超過 7 天則整筆不採計。
- **第一次執行必須大聲失敗**：沒有前一次觀測時回報 0 會被當成「持平」，那是假訊號。
  此時仍會把快照落地，否則明天一樣沒得比，會永遠卡在「無前一次觀測」。

#### 計分

規格第124行只給五個等級，**沒有給金額門檻**。因此方向由淨流正負決定，「大幅」與否
以這個數列**自己的歷史規模**判定，而不是自行發明「超過 X 億美元算大幅」
（同 Gate B 用滾動百分位而非寫死絕對值的原則）。

規模單位取歷史淨流**絕對值**的中位數——流出期間的規模同樣是規模，只看正值會讓
熊市完全沒有比較基準：

| 相對常態規模 | 分數 |
|---|---|
| < 0.3 倍 | 0（持平）|
| 0.3 – 2 倍 | ±1 |
| > 2 倍 | ±2（大幅）|

刻意**不用百分位當「持平」的門檻**：規格的持平指進出接近打平，不是「跟平常差不多」。
若資金流長期都很大，它的後 20% 依然是很大的金額，把那叫持平就錯了。

**不足 20 筆歷史時只判方向、不判強度**，信心標「中」——方向是確定的，但「大幅與否」
還沒有依據，與其硬給 ±2 不如少說一級。計算時排除當日自己那筆，否則等於部分拿自己
當比較基準。

資料檔：`docs/data/etf_snapshots.csv`（逐檔規模快照，供計算差額）與
`docs/data/etf_flows.csv`（每日淨流，供判定強度）。

ETF.com 的解析器仍保留在 `sources/etf_flows.py` 並有測試涵蓋，
若日後從可存取的網路環境執行仍可使用，但預設流程不再呼叫它。

### ③ NDX 成分股與市場廣度

抓取順序：**TradingView（主）→ 未過期的快取 → Invesco QQQ 持股 → 維基百科 →
過期的快取（最後手段）**。

#### TradingView（主來源）

TradingView 的 screener 端點一個請求就回傳**成分股清單與每檔的均線、RSI、
漲跌幅、市值**，取代原本「先取得清單，再用 yfinance 逐檔下載 220 個交易日
收盤價自行算 200 日均線」那整段——約 100 次下載換一個百分比。

因為同一份資料本來就含這些欄位，順帶算出的指標一併輸出到報告的
`ndx_breadth_detail` 並顯示在儀表板：

| 指標 | 用途 |
|---|---|
| 站上 200 日線比例 | **③ 的計分依據**（> 70% 得 +1，< 30% 得 −2）|
| 站上 50／20 日線比例 | 單看 200 日線分不出「短線鬆動」與「中期轉弱」|
| 漲跌家數、A/D 比 | 當日廣度 |
| RSI 中位數、超買/超賣家數 | 動能分布 |
| 接近 52 週高／低家數 | 極端值分布 |
| 前十大市值占比 | NDX 極度集中於少數幾檔，這是判讀「廣度」不可少的背景 |

每個百分比都會一併回報**計算樣本數**：若有幾檔缺均線資料，分母就不是成分股
總數。不講清楚的話，「62%」看起來一樣正常，但可能是 62/98 而不是 62/100。

這個端點沒有官方文件、請求格式可能變動，因此會依序嘗試幾種已知格式，
**每一種都記下實際結果**（狀態碼、回傳筆數、內容前綴），全部失敗時把這些
證據一起拋出並退回備援來源。盲改再重跑一次要好幾分鐘，訊息裡沒有證據就只能猜。

#### 備援來源（`docs/data/ndx100_constituents.json`）

2026-08 實測兩個備援的自動來源都不可用：

- Invesco 的下載網址回傳的是 React 產品頁的 HTML，不是 CSV 檔
- 維基百科 Nasdaq-100 條目**已經沒有成分股表格了**（該頁18個表格中最大的是41列的
  年度報酬表，成分股清單已不在該頁）

因此實務上請**手動維護一次**這個檔案，之後每季調整時更新即可（成分股一年只換4次）：

```json
{
  "as_of": "2026-08-08",
  "tickers": ["AAPL", "MSFT", "NVDA", "..."]
}
```

放進去之後，程式會優先使用它；即使超過快取有效期、且兩個線上來源都失敗，
仍會退回使用這份清單（並在日誌標明是用了哪一天的舊清單）。這份清單是你提供的
真實資料，不是程式臆測出來的內容，所以採用它不違反誠實原則。

沒有這個檔案時，③ 的廣度子項會標記「暫缺」，但 ③ 仍由 MOVE 指數正常計分。

**先前「Actions 連不到 federalreserve.gov」的說法是錯的。** 補上逐來源診斷後
實測，錯誤其實是 **HTTP 404**——網站完全連得到（404 代表 DNS、TCP、TLS、HTTP
全部成功），只是那個年度索引網址早已不存在。之所以誤判，正是因為原本的錯誤訊息

現在索引依序嘗試四個來源，**RSS 排最前面**（機器可讀的正式發布管道，比解析

1. `feeds/press_monetary.xml`（RSS）
2. `monetarypolicy/fomccalendars.htm`（FOMC 行事曆頁）
3. `newsevents/pressreleases/{year}-monetary.htm`（原本的年度索引）
4. `newsevents/pressreleases/{year}-press.htm`

抓取失敗仍會退回人工填入的分數，並在備註標明實際的失敗原因（含狀態碼）。

# 模組二：分析師估值與市價差異比較

蒐集美股分析師共識目標價與每日收盤價，計算「上漲空間」
（=（共識目標價 − 收盤價）／收盤價），並提供可依類股篩選、排序的比較儀表板，
用來尋找分析師共識價明顯高於市價的標的。

## 架構

```
analyst_valuation/
  config.py               股票池來源、資料源設定、品質門檻
  sources/universe.py     S&P 500 成分股 + GICS 類股別（維基百科）
  sources/yahoo_targets.py    Yahoo Finance 共識目標價（免金鑰，預設啟用）
  sources/finnhub_targets.py  Finnhub 共識目標價（選用，需免費API金鑰）
  sources/prices.py       批次收盤價 + 近一週/近一月漲跌幅
  aggregate.py            多來源平均、上漲空間、信心等級（純函式）
  pipeline.py             併發抓取與彙整
  storage.py              輸出到 docs/data/valuation/
scripts/run_valuation.py  進入點
docs/valuation.html + valuation.js   儀表板頁面
```

## 使用方式

```bash
python3 scripts/run_valuation.py -v              # 全部 S&P 500
python3 scripts/run_valuation.py --limit 20 -v   # 只跑前20檔，快速驗證
FINNHUB_API_KEY=xxx python3 scripts/run_valuation.py -v   # 啟用第二個目標價來源
```

## 儀表板功能

- **統計方塊**：資料基準日、涵蓋檔數、中位數上漲空間、共識價高於現價的比例、
  中位數機構數、中位數離散度
- **各類股中位數上漲空間**：橫向長條圖，一眼看出哪些類股整體被看好
- **個股比較表**：代號／公司／類股／**市值**／收盤價／共識目標價／上漲空間／**機構數**／
  **目標價區間（低－高）**／**離散度**／近一週／近一月／信心等級，所有欄位可點擊排序
- **目標價區間視覺化**：每列有一條小軌道，兩端是最低與最高目標價，
  ● 標出目前收盤價的位置、▍標出共識目標價的位置，一眼看出現價落在分析師預期區間的哪裡
- **篩選**：類股、信心等級、最低上漲空間、**最少機構數**、**市值**、**股價淨值比**、
  **最高離散度**、代號或公司名稱搜尋、是否隱藏無目標價標的

### 離散度（價格分歧程度）的定義與限制

```
離散度 = (最高目標價 − 最低目標價) / 共識目標價 × 100%
```

數值越大代表各機構對該股的看法越分歧。UI 以顏色分級：≤30% 綠（共識度高）、
30–60% 中性、≥60% 橘（分歧大）。

**這是以區間寬度估算的代理指標，不是統計上的標準差。** 資料來源只公布
最高／最低／平均／中位數，不提供每一家機構的個別目標價，因此無法計算真正的
標準差或四分位距。這個估算會被單一極端值放大，機構數少的時候尤其不穩定，
所以表格把「機構數」放在旁邊，兩個要一起看。

高低價、中位數與離散度一律取自**同一個資料來源**（優先 Yahoo，記錄於 `range_source`
欄位）——分子（最高−最低）與分母（平均）若來自不同的分析師樣本，算出來的數字沒有意義。
但 `consensus_target` 仍是各來源共識價的平均，兩者用途不同。

## 目標價的蒐集方式：逐機構去重後自行計算平均

資料源分成兩層，**有逐機構資料時一律優先，並自行計算平均**：

| 層級 | 來源 | 狀態 | 提供內容 |
|---|---|---|---|
| **A. 逐機構** | FMP | 選用，需 `FMP_API_KEY` | **每一家券商各自的目標價**（含機構名稱與發布日）|
| B. 共識 | Yahoo Finance | 預設啟用，免金鑰 | 僅彙總後的 mean/median/high/low + 分析師家數 |
| B. 共識 | Finnhub | 選用，需 `FINNHUB_API_KEY` | 另一組獨立彙總的共識目標價 |

### 逐機構模式（basis = `per_firm`）

取得逐機構資料時，流程是：

1. **蒐集**各來源的個別券商目標價
2. **依機構去重**：同一家券商只採計一次，取最新一份報告
3. **自行計算**平均／中位數／最高／最低——不沿用任何資料源的彙總值

去重是必要的：同一家券商在不同來源會有不同寫法，不正規化就會被當成多家、
讓平均值被重複計票的機構拉偏。`firms.py` 會把
`J.P. Morgan Securities LLC`、`JPMorgan Chase & Co.`、`JP Morgan` 一律正規化為同一鍵值
（去標點、去 Securities/Capital/Group 等修飾詞、再套用別名表）。

輸出中的 `duplicates_removed` 會記錄合併掉幾筆，儀表板的列 tooltip 也會列出
**每一家券商的目標價**，讓算出來的平均可以被逐筆檢驗。

### 共識模式（basis = `consensus`）

沒有逐機構資料時退回此模式：`consensus_target` 為各啟用共識來源的平均。
此時**無法依機構去重**（來源只給彙總值），UI 與 JSON 都會標明 basis 為 `consensus`，
不會假裝做過機構層級的計算。

### 為什麼不逐一爬各財金網站

各大財金網站（Yahoo、MarketWatch、TipRanks、Finviz…）呈現的都是**同一批券商報告的
彙總共識價**，而非各站獨立的估值；逐站抓取再平均，多半只是把同一份共識重複計算。
此外 Finviz、TipRanks 的服務條款明文禁止自動化擷取，也沒有公開 API。
真正能增加資訊量的是「拿到每一家券商的個別報告」，也就是上面的 A 層。

### 配合免費方案限制的節流與熔斷

各資料源的免費方案有硬限制，抓取又是多執行緒並發，不處理就會整批失敗：

| 來源 | 免費方案限制 | 本專案的處理 |
|---|---|---|
| Yahoo | 無公開上限，實測為滾動視窗總量 | 節流到 **120 calls/min**（`YAHOO_CALLS_PER_MIN`，每檔兩個請求 ≈ 60 檔/分）；回報限流即熔斷，未處理的標的順延 |
| Finnhub | 60 calls/min | 節流到 **55/min**（`FINNHUB_CALLS_PER_MIN`），跨執行緒共用同一個限流器 |
| FMP | price-target 端點**需付費方案**（回 402）| 熔斷：第一次遇到 402 就停用該來源，不再對其餘標的重複請求 |

Yahoo 的數字來自實測而非文件：全市場掃描時 300 檔那批安然通過，1500 檔那批在
大約第 465 檔之後整批回 `YFRateLimitError`。可見它限的是滾動視窗內的總量，
所以要壓到能長時間維持的水準，並靠「每天多班次執行」而不是「單次跑更快」來掃完全市場。

- **暫時性錯誤（429、5xx）不熔斷**，只有方案／授權類錯誤（401/402/403）才會——
  重試那些狀態碼沒有意義，而且會白白消耗配額。
- 被熔斷的來源會在報告的 `disabled_sources` 與 UI 說明列**一次講清楚**，
  而不是每一檔重複一遍同樣的錯誤。

實測結果（2026-08）：FMP 免費金鑰對 `/stable/price-target-news` 回
`402 Payment Required`，因此**逐機構模式需要 FMP 付費方案**；未升級時系統會
自動退回共識模式並明確標示，不影響其餘功能。

### ⚠️ 憑證絕不可進入輸出

Finnhub 把金鑰放在 query string，`requests` 的 `HTTPError` 訊息包含完整 URL。
2026-08 曾因此把金鑰寫進 `notes` 並 commit 進公開 repo。

現在任何來自外部呼叫的例外訊息，都必須先經過 `secrets_redaction.redact_secrets()`
才能進入輸出或日誌；`storage.save_report()` 落地前還會再過一次，
所以單一來源的疏忽不足以造成外洩。**新增資料源時請沿用這個規則。**

### 啟用逐機構模式

到 https://site.financialmodelingprep.com/developer/docs 申請金鑰，
在 repo 的 Settings → Secrets and variables → Actions 新增 `FMP_API_KEY`。
（同理，`FINNHUB_API_KEY` 可加入第二個共識來源。）

## 模組五：美股總體經濟指標觀察

27 條 FRED 序列，分為六類：成長動能／就業市場／通膨／利率與殖利率曲線／
金融條件／消費與房市。

### 三個容易出錯的地方

**1. 「最新值」永遠是過去某一期的數字。** CPI 的 7 月數字要到 8 月中才公布、
Case-Shiller 房價落後約兩個月。每一列都標明**參考期**與**落後天數**——
把它當成「今天的狀況」是總經數據最常見的誤讀。

**2. 水準 vs 變化，用錯不會報錯。** CPI 原始序列是指數（314.5），要看的是
年增率；失業率原始序列本身就是百分比，再算一次年增率毫無意義；非農就業
要看的是「這個月增加幾人」，不是總就業人數 1.6 億。因此每一條序列都在
設定檔裡明確標出轉換方式（`level`／`yoy`／`mom`／`diff`），填錯會直接拋錯。

**3. 「還沒公布」不等於「來源壞了」。** 兩者在畫面上都是沒有新數字，但處置
完全不同——前者等就好，後者要去修。判定門檻依**各序列自己的發布節奏**設定：
週頻的初領失業金 21 天、季頻的 GDP 150 天。用單一門檻的話，不是誤報就是漏報。

### 方向好壞由設定檔指定，不由程式推論

失業率上升是惡化、GDP 上升是改善——這件事程式無從推論，因此寫在設定裡。
**通膨與殖利率這類沒有單一方向好壞的指標一律顯示「—」**，不硬套。

### 每日掃描並記錄實際發布日

FRED 的資料只帶「參考期」，不帶「這個數字是哪天公布的」。`publish_lag_days`
原本是依各機構慣例**手填的估計值**——而手填的東西已經出過一次錯（過期門檻
誤報 7 條）。

因此改成**觀測**：每天掃一次，當某條序列的最新參考期往前推進時，就把「今天」
記成那一期的觀測發布日（`data/macro/release_log.csv`）。累積之後就有本專案
自己量到的發布節奏，畫面上與手填估計值並列，差距就是估計的誤差。

三件事特別處理：

- **修正不算發布**：數值被事後改動而參考期不變，那是修正。算成發布的話，
  觀測到的時滯會被大量假訊號污染。
- **掃描紀錄要另外存**（`scan_log.csv`）：少了它，「資料停止更新」與
  「排程壞掉沒跑」在日誌上長得一模一樣。
- **累積不足兩期不顯示**：一期算不出節奏，硬給數字會讓人以為那是量出來的。

觀測誤差的方向是固定的：掃描為每日一次，因此最多**高估一天**。這一點寫在
畫面上，不假裝沒有。

### 延遲 vs 停止更新

兩者畫面上都是「沒有新數字」，處置卻完全不同：延遲等就好，停止更新該從
清單移除。超過過期門檻**四倍且至少一年**判定為停止更新，單獨列出。

實測 USSLIND 落後 2384 天 / 門檻 90 天 = 26 倍——遠超過任何合理的延遲，
已移除。

### 每項指標的深入分析

點選單一指標會展開，全部是**可查證的量**，不壓成單一分數：

| 分析 | 回答什麼 |
|---|---|
| z 分數（全期／10年） | 離平均幾個標準差。與百分位互補——分布有厚尾時兩者印象很不一樣 |
| 三個月加速度 | 變化的變化。水準仍在上升但速度在放慢，只看「三個月變化」看不出來 |
| 歷史極值與區間位置 | 最高／最低是多少、什麼時候、目前落在區間哪裡 |
| 上一次轉折 | 上個高點／低點距今幾期。**最近 6 期不判定**——轉折要後續資料才確認得了 |
| 波動狀態 | 近期波動相對長期。波動放大往往先於水準的轉折 |
| **衰退期對照** | 這條指標在 NBER 衰退期與擴張期的分布，以及目前值落在兩者之間何處 |

衰退期對照是其中最有價值的：同一個失業率 4.1%，在擴張期的分布裡與在衰退期
的分布裡意義完全不同。把兩組分布擺出來，比任何自訂門檻都誠實——而且畫面
明說**那是分布位置，不是衰退機率**，單一指標算不出機率。

### AI 摘要：官方發布原文，不是二手新聞

各指標的最新變動由 AI 摘要說明，來源是**該指標的官方統計發布原文**
（BLS／BEA／Census／Fed 等）——CPI 變動的原因，最準確的來源就是 BLS 那份
新聞稿本身，它逐項說明哪個分類推升了指數。二手新聞只是在轉述它，還會混入評論。

**三道反幻覺防線**（沿用 FOMC 判讀那一套，這裡更需要）：

1. **抓不到文件就不呼叫模型。** 讓模型憑記憶說明「上個月 CPI 為什麼上漲」，
   會得到一段完全通順、細節具體、而且是編造的解釋。**散文比數字更危險**
   ——數字錯了看得出來，一段流暢的解釋不會有人懷疑。
2. **原文佐證逐字比對。** 模型必須附上文件中的原句；對不上就**整份摘要作廢**，
   而不是只丟掉引句——引句編得出來，摘要同樣不可信。
3. **只摘要，不預測。** 提示詞明確禁止預測未來與投資判斷，輸出也不留那種欄位。

畫面上摘要、原文佐證、來源連結三者一起顯示。只給摘要的話，讀者無從判斷
那句話是文件裡真的有，還是模型補出來的。

**只在指標更新時呼叫**：以「當期摘要存不存在」為判準，而不是「發布日誌記錄過
這一期」——後者會讓今天 API 出錯的指標明天不再重試，那一期就永遠沒有摘要。

殖利率、利差、通膨預期等**市場價格類指標沒有對應的統計發布**，因此沒有摘要。
硬配一個來源，只會讓模型對著不相干的文件生出一段像樣的解釋。

#### 首次執行的實測結果（Actions，2026-08）

成功 **4 條**：工業生產（Fed G.17）、PCE 物價（BEA）、新屋開工（Census）、
30年期房貸利率（Freddie Mac）。四則都通過原文逐字比對。

失敗依原因分四類，處置完全不同：

| 原因 | 項數 | 該怎麼辦 |
|---|---:|---|
| 本來就沒有來源 | 9 | 市場價格類指標，正常狀態不是故障 |
| **來源封鎖** | **6** | `bls.gov` 全站對資料中心 IP 回 **403** |
| 內容不符 | 4 | 網址指向入口頁而非發布頁，該檢查網址 |
| 模型或 API 出錯 | 1 | 下次執行自動重試 |

（「來源封鎖」那六條，加上同屬 BLS 的 JOLTS，已於下一節處置為 `accepted`，
往後不再列為封鎖。）

**BLS 封鎖是最大的損失**：CPI、核心 CPI、就業報告（失業率／非農／參與率／
薩姆規則）、JOLTS 共六條——也就是最重要的通膨與就業指標——都拿不到官方
發布文字。三個不同路徑皆回 403，是 host 層級的封鎖，換路徑沒有用。
這與 ETF.com、CME 是同一種情況。

**處置（2026-08-12 更新）：這七條已經救回來了。** 原本的結論是「接受沒有摘要」，
理由是「bls.gov 全站 403、沒有替代來源可換」——**後半句從來沒有查證過，而且是
錯的**。當時確認了「www.bls.gov 擋我們」，就直接跳到「這幾條拿不到」，中間少了
一步：去問還有沒有別的路。

實測 Wayback 存檔拿得到同一份 BLS 原文，見下一節。

`UNAVAILABLE_SOURCES` 機制本身保留（目前為空）：日後真的遇到查證過、確實無路
可走的來源時，該有的處置仍然是「明講接受」而不是靜靜刪掉。但進入那個名單的
門檻是**查證過沒有別的路**，不是「主要來源擋住了」。

### 找替代來源：先驗證，再採用

`scripts/probe_sources.py` + `.github/workflows/probe-sources.yml`（手動觸發）。

**為什麼要有這一步。** 開發環境沒有對外網路，在那裡任何網址都驗證不了。
先前憑印象加了一個沒驗證過的 FRED 端點，實測回傳 HTML、那個端點根本不存在，
卻已經在報告裡佔了一個「已嘗試」的位置。所以流程分兩步：探測器在 Actions 裡
跑並記錄實際結果，看過真實結果之後才把通過的網址寫進 `RELEASE_SOURCES`。
**探測器不會自動採用任何來源**——自動採用只是把「沒驗證」換個地方藏起來。

四道檢查缺一不可，只看 HTTP 200 會放進一堆入口頁：

| 檢查 | 擋掉什麼 |
|---|---|
| `status` | 403／404 |
| `final_url` | 302 轉回首頁再回 200——只看狀態碼會把首頁當發布頁 |
| `topic` | 五千字的導覽選單（夠長、200，但與指標無關） |
| `recency` | 靜態說明頁：講「這項指標是什麼」，沒有這一期的數字 |

最後一道正是那四條「內容不符」的病灶。判定結果分
`usable / blocked / redirected / too_short / off_topic / stale_page / error`，
每一列都寫出為什麼——只寫「可用／不可用」的話，「來源改版了」與
「我們挑錯頁面」在報告上又會長得一模一樣。

探測的候選分三類：`data.bls.gov`（測 403 是不是只針對 `www` 主機）、
Wayback 快照（文字仍是 BLS 原文，代價是可能落後幾天）、主流媒體報導頁。

#### 首次探測結果（Actions，2026-08-12）

探測 30 個網址，**10 個可用**。判定分布：`blocked` 7、`http_error` 6、
`off_topic` 5、`stale_page` 2。

| 指標 | 採用的來源 | 實測 |
|---|---|---|
| CPI／核心 CPI | Wayback 存檔的 BLS `cpi.nr0.htm` | 20,741 字，主題命中 4 |
| 失業率／非農／參與率／薩姆規則 | Wayback 存檔的 `empsit.nr0.htm` | 11,421 字 |
| JOLTS | Wayback 存檔的 `jolts.nr0.htm` | 5,453 字 |
| 零售銷售 | `census.gov/retail/sales.html` | 2,679 字 |
| PCE／核心 PCE | `apps.bea.gov/newsreleases/national/pi/` | 10,513 字 |

三個被否決的方向，各自是一個獨立的結論：

- **`data.bls.gov` 也回 403** —— 封鎖是機構層級，不是 `www` 專屬。原本的診斷成立。
- **AP News hub 沒有用** —— `/hub/inflation` 回 200 但只命中 1 個主題關鍵詞
  （典型的 JS 列表外殼），`/hub/jobs` 直接 404。若當初憑「AP 有報導 CPI」就把它
  加進設定，得到的會是一個每天回 200、內容卻與指標無關的來源。
- **NFCI 兩個網址都是 `stale_page`** —— 芝加哥聯準銀行把 NFCI 當**資料**發布，
  沒有隨期別更新的敘述可摘要。這不是網址挑錯，是這條指標本來就沒有發布文字，
  歸到「本來就沒有來源」才對。

另外修正了探測器自己的一個錯：薩姆規則原本的主題關鍵詞填的是
`recession／labor market／Sahm`——那是**這條指標的用途**，不是發布原文會出現的
字，於是就業報告被誤判成 `off_topic`。主題關鍵詞要描述文件寫了什麼，
不是我們拿它來做什麼。

#### 用存檔就必須加的一道檢查：期別比對

Wayback 給的是「**最新的快照**」，不是「最新的發布」。快照停在上一期時，
文件本身完全真實、引句逐字對得上、摘要讀起來毫無破綻，只有一件事是錯的：
它講的是六月，而我們把它掛在七月的數字底下。

**反幻覺的三道防線全都擋不住這種錯**，因為模型並沒有編造任何東西。

因此 `assert_document_covers_period()` 在送模型之前比對期別：月頻要求出現月份名
與年份，季頻要求出現「second quarter」這類措辭，週頻與日頻不做（那些發布不用
「某月」指稱期別，硬比只會誤殺）。對不上就不送模型，並歸類為「內容不符」。

這道檢查對官方頁面同樣必要——入口頁常年掛著上一期的內容，那正是先前那幾條
「內容不符」的成因。

**關於二手報導。** 原始需求是「蒐集對應新聞並摘要」，是本專案自己把範圍收窄成
官方發布的。這次探測的結論是：**不需要退到二手**。Wayback 提供的仍是官方原文
逐字，比任何轉述都準確。二手來源留在候選清單裡，但目前一條都沒有採用。

### FEDFUNDS：病灶是挑錯文件，不是來源不給

這一條已直接修好，不必等探測結果。原本指向 `press_monetary.xml`——那是**發布
索引的 RSS**，去標籤之後只剩一串標題，當然看不出這一期的利率決定。

正確的文件是「最近一次 FOMC 聲明」，而它的網址每次會議都不同，硬填靜態網址
必然指到索引頁。改用 `news_ai.RESOLVERS`：呼叫模組一已經在用的
`fomc.latest_meeting_on_or_before()`——那個索引鏈（RSS 優先、四個候選）早就
修過並每天在跑，是有實績的解析器，不是新猜的來源。

### 沒有自創的綜合分數

本模組不把 27 條指標壓成一個數字。呈現的是每條指標的水準、三個月與十二個月
變化、以及在最近 20 年分布中的百分位。少數帶有既定門檻的指標（薩姆規則 0.50、
NFCI 的 0）都是**原作者或編製機構定義的**，不是本專案自訂。

## 模組四：類股資金輪動觀察

每個交易日收盤後監看十一個 GICS 類股（SPDR 類股 ETF）的漲跌、相對大盤強弱，
以及由 ETF 申贖流量算出的資金動能。

### 三層資訊

1. **各期間漲跌**：當日／近一週／近一月／近三月，可切換為「相對大盤的超額報酬」
2. **輪動四象限**：橫軸相對強弱（RS＝「類股÷大盤」相對它自己 63 日均值，100 為持平）、縱軸 RS 的 10 日動能

   | | 動能為正 | 動能為負 |
   |---|---|---|
   | **RS ≥ 100** | 領漲 | 轉弱 |
   | **RS < 100** | 改善 | 落後 |

   輪動發生在「轉弱」與「改善」兩格。漲幅排行只告訴你過去誰強，
   象限告訴你資金正在往哪走。
3. **資金流**：由 ETF 流通股數變化計算——股數只會因申購／贖回而變動，
   因此「Δ股數 × 價格」就是流入／流出該類股的金額**本身**，不是代理指標。

### 三個容易出錯的地方

- **視窗一律以交易日計**（近一週＝5 個交易日、近一月＝21 個），不用日曆天：
  連假前後的日曆週會是不同長度的區間，跨日期比較沒有意義。
- **缺值不能變成 0**：XLC 2018-06、XLRE 2015-10 才成立。把缺值當成 0% 報酬，
  排名時會排到中間，看起來完全正常；當成最差，則會讓「還沒成立」看起來像
  「表現最爛」。兩者都不對——缺值就是不參與排名。
- **超額報酬必須用同一視窗的基準**：拿類股的近一月去比基準的近三月，
  算出來的只是兩段不同區間的差。
- **相對強弱不能錨在抓取視窗的第一天**：第一版把比值標準化成「起點 = 100」，
  而起點就是 `HISTORY_DAYS` 決定的那一天——改一個設定常數，所有類股的 RS
  就整批位移、四象限歸類跟著變。實測首次執行 11 檔裡有 9 檔 RS < 100，
  象限嚴重偏左，純粹因為那段期間大盤贏過多數類股。那不是輪動訊息，
  是錨點造成的假象。改為與**自己的 63 日移動平均**比較，數值不再依賴視窗長度。

### 資金流的兩道防線（沿用模組一的教訓）

- **股數可信度**：對 ETF 而言「股數 × 價格」依定義等於淨資產，對不起來就代表
  其中一個數字是錯的。不可信時退回淨資產分解（估計），並在畫面上標明「估計」
  ——兩種基礎的數字不可直接相比。
- **陳舊資料**：實測 Yahoo 的 totalAssets 對 ETF 不是每日更新。整批數值與前一次
  完全相同時回報 0 會被讀成「資金持平」，那是假訊號。判斷依據放在原始欄位，
  不在算出來的差額——差額為零時兩種成因長得一模一樣。

資金流以**佔自身淨資產的比例**呈現：XLK 的規模是 XLRE 的十幾倍，比絕對金額
等於在比誰規模大，不是在比誰的資金動能強。

## 全美股逐檔抓取（模組二的擴充）

除了 S&P 500 的每日彙總，另有一條「**全美股上市公司逐檔抓取**」的流程，
處理約 8000+ 檔、可續跑、失敗自動重試、每一檔的結果逐筆保存。

```
data/universe.csv     公司清單（ticker, name, exchange, is_etf, source）
data/ledger.csv       抓取帳本（status, attempts, last_attempt_at, last_ok_at, last_error）
data/results/A.jsonl  逐檔結果，依代碼首字分片，一行一檔

docs/data/valuation/universe_latest.json   儀表板讀的彙整結果
```

### 使用方式

```bash
python3 scripts/build_universe.py -v                                  # 1. 建立公司清單
python3 scripts/fetch_universe.py --new-cycle -v                      # 2. 開新一輪（全部重抓）
python3 scripts/fetch_universe.py --max-tickers 1500 -v               # 3. 續跑（可重複執行）
python3 scripts/publish_universe.py -v                                # 4. 產生儀表板資料
python3 scripts/fetch_universe.py --new-cycle --keep-ok -v            #    只補跑沒成功的

python3 scripts/fetch_universe.py --include-all -v                    #    連非普通股也一併抓
```

「抓取」與「產生報告」刻意分開：抓取跨多次執行、要跑好幾小時，重出報告只要幾秒。
每批抓完就重出一次，儀表板便能隨掃描進度更新，不必等整輪跑完。

### 儀表板怎麼看這份資料

模組二頁面上方有「S&P 500／全美股」切換鈕，兩者共用同一套渲染與篩選程式碼
（上漲空間、離散度、信心度的定義只能有一個實作，否則兩邊會慢慢算出不一樣的數字）。

全美股是跨班次累積的，因此頁面會顯示**本輪掃描進度**——沒有這段，讀者無法分辨
「這檔沒有分析師覆蓋」與「這檔今天還沒輪到」。另外兩個為了全市場規模而做的處理：

- **疑似異常預設隱藏**：目標價相對現價偏離超過 300%（或低於 −90%）者，多是單一
  分析師覆蓋的極低價股。不濾掉的話，「上漲空間」榜首會清一色是「現價 0.27 美元、
  目標價 4.8 美元」這種列，真正被低估的中大型股會被埋在幾百列之後。這些列會標記、
  排到最後、且不列入類股中位數，但**不刪除**，取消勾選即可看到。
- **表格最多列出 300 列**：篩選與排序仍在全部資料上進行，只是渲染截斷——7,498 列
  一次全塞進 DOM 會讓瀏覽器卡住好幾秒，而且沒有人會捲到第 500 列。

#### 類股名稱統一到 GICS

兩份資料源用的是不同的分類體系：S&P 500 清單帶的是 **GICS** 官方名稱，全市場掃描
則取自 **Yahoo**。同一個畫面、同一個「類股」下拉，切換資料源後選項卻整批換一套名字：

| Yahoo | GICS |
|---|---|
| Technology | Information Technology |
| Healthcare | Health Care |
| Consumer Cyclical | Consumer Discretionary |
| Consumer Defensive | Consumer Staples |
| Financial Services | Financials |
| Basic Materials | Materials |

（Communication Services／Industrials／Energy／Utilities／Real Estate 兩邊同名。）

因此在 `aggregate.normalize_sector()` 統一到 GICS 這一套，兩條資料路徑都會經過它。
未知名稱一律**原樣保留**——日後資料源多出新類別時，照原樣顯示比硬塞進某個既有類別
要好，後者會讓一整群標的無聲地被歸錯類。

> ⚠️ 這只統一**名稱**，不統一**分類判斷**。兩家供應商對個別公司的歸類本來就可能
> 不同：某檔在 Yahoo 是 Technology，在 GICS 官方未必被分到 Information Technology。
> 這裡做的是讓詞彙一致，不是宣稱兩邊的分類結果相同。

### 市值篩選

市值取自同一份 `info` 回應（與類股、每股淨值同批取得，不需額外請求）。

篩選提供兩種語意，共用一個下拉：

- **最低門檻**：≥ $200B／$10B／$2B／$300M。`≥ $2B` 特別實用——全市場範圍內
  「上漲空間 300%」幾乎清一色是單一分析師覆蓋的雞蛋水餃股，設個市值下限就
  能把它們一次濾掉。
- **單一級距**：巨型（≥ $200B）／大型（$10B–200B）／中型（$2B–10B）／
  小型（$300M–2B）／微型（$50M–300M）／奈米（< $50M）。
  分界採美股慣用值，非自訂。

分級門檻**只定義在前端一處**（`docs/valuation.js` 的 `CAP_TIERS`）。後端只送
市值原始值與「這個數字能不能用」——門檻若兩邊各存一份，改了一邊就會悄悄不一致。

#### 幣別必須一致，否則比大小沒有意義

市值篩選是拿數字比大小，單位不同就不能比。資料源給的市值以該檔的計價幣別為準，
若混進非美元的數字，一檔日圓計價的中型企業會被算成「巨型股」排在名單最上面
——**不會報錯，只會靜靜給出一個看起來完全正常的排名**。

因此幣別不是 USD 就不採用，畫面顯示「非美元」而非留白（留白會跟「查無資料」
混在一起）。幣別**缺值**時則照常採用：這份股票池全是美國掛牌，預設就是美元，
把「沒寫幣別」當成可疑會讓大量正常標的平白消失。

幣別必須取自**提供該市值的那一筆報價**（記錄中另存為 `market_cap_currency`）。
記錄裡原有的 `currency` 取自主要報價來源，未必是同一筆——拿甲來源的幣別去驗
乙來源的市值，這道防線就形同虛設。

### 資料歷史長度的實測結論（模組三回測）

回測需要十五年歷史，而「抓得到最新值」不等於「抓得到歷史」。實測結果：

| 指標 | 涵蓋率 | 結論 |
|---|---:|---|
| 融資餘額年增率 | 0.1% → **100%** | FINRA 頁面表格只列近 13 個月，改為同時掃頁面上的歷史檔連結後補齊 |
| HY OAS 水準／20日變化 | **19.9% / 19.4%** | FRED 對此序列限制在近三年（ICE BofA 為授權資料），無解 |
| SOFR-IORB 利差 | **33.5%** | SOFR 2018-04、IORB 2021-07 才開始發布，是利率本身的存在期間 |
| 其餘 10 項 | 100% | — |

#### FRED 的限制是針對單一序列，不是通用的

端點診斷確認：

```
BAMLH0A0HYM2  帶區間 785 筆 / 2023-08-11，不帶區間完全相同
SOFR          2086 筆 / 2018-04-03   <- 該利率本身的起始日
IORB          1840 筆 / 2021-07-29   <- 同上
```

曾嘗試 `fred.stlouisfed.org/data/<ID>.txt` 作為第三條路，**實測回傳 HTML 頁面
——該端點不存在**，已移除。

#### 替代序列已量測並否決

`BAA10Y`（穆迪 Baa 對 10 年期公債利差，1986 年起、無授權限制）看似可以頂替，
但在 751 個交易日的重疊期間實測：

- 水準相關 **0.559**（需 ≥0.8）
- **日變化相關 0.121**（需 ≥0.7）

兩項 HY OAS 指標中有一項是「20 日變化」，日變化相關只有 0.12 代表兩者的
短期訊號幾乎無關。換上去只是換了一個同名的不同指標——**比缺資料更糟，
因為畫面上看不出來**。維持現狀，並保留這項量測（重疊期間會隨時間變長，
數字若改變即可重新判斷）。

### 淨值篩選

每股淨值取自同一份 `info` 回應（與類股同批取得，不需額外請求），
股價淨值比則**用本專案自己的收盤價計算**而不是沿用資料源的現成比值——
否則分子（畫面顯示的收盤價）與分母（資料源當時的價格快照）來自不同時點，
使用者拿收盤價除以淨值會得到跟欄位不一樣的數字（同離散度的處理原則）。

儀表板可依「股價淨值比 < 1／1.5／2／3」篩選，`< 1` 代表市價低於帳上股東權益。

#### 「算得出來但不能用」的兩種情況

比值算得出來不代表它有意義。這兩種列會標示原因、**不列入篩選結果**，
而且顯示的是原因而不是留白——留白會與「查無資料」混在一起，但意義完全不同：

| 標示 | 情況 | 為什麼不能用 |
|---|---|---|
| 負淨值 | 股東權益為負（33/503 檔，如 ABBV、MO、AZO）| 負除以負得正，財務惡劣的公司會看起來很便宜 |
| 股別不符 | 價格與淨值不是同一種股別 | 見下 |

**股別不符**的實測案例是 BRK-B：收盤價 521.80，但資料源給的每股淨值是
**505,559**——那是 A 股的數字（B 股為 A 股的 1/1500）。算出來 P/B = 0.001，
會直接登上「最便宜」榜首。門檻設在 `IMPLAUSIBLE_PB_FLOOR = 0.05`：真正陷入
困境的公司大約落在 0.2 上下，0.05 以下只可能是單位對不上。刻意**不猜換算比例**
——猜錯會產生一個看起來很合理、實際上錯誤的數字。

高端不設限：GDDY 1718、CL 315 這類是實打實的，大量庫藏股買回讓帳上股東權益
逼近於零，比值自然極高，那不是資料錯誤。

### 抓取範圍：只抓普通股

清單保留全部 7,498 檔證券與其分類（`security_type` 欄位），但**預設只抓普通股**
（含 ADR 與合夥事業單位），共 5,958 檔。實測依據：

| 種類 | 檔數 | 有分析師目標價 |
|---|---:|---:|
| 普通股（含 ADR、MLP）| 5,958 | **70.0%** |
| 認股權證 | 478 | **0.0%** |
| 特別股 | 505 | ~1% |
| SPAC 單位 | 271 | — |
| 債券 | 167 | — |
| 權利 | 119 | — |

排除的 1,540 檔佔掉五分之一的抓取預算，實測覆蓋率合計僅 2.2%；以已抓取的
1,009 檔驗證，**排除後失去的有覆蓋標的為 0 檔**。認股權證與債券本來也不是公司。

過濾在讀取端做（`analyst_valuation/universe_file.py`），抓取端與發布端共用
同一個定義——兩邊各寫一份的話，儀表板會出現「有結果但不在清單裡」的列，
而且沒人會發現是定義不一致造成的。要全部納入時加 `--include-all`，不必重建清單。

#### 分類靠的是「這張證券是什麼」，不是「它代表什麼」

證券名稱裡有兩種資訊，混在一起看就會出錯：

```
Itau Unibanco ... American Depositary Shares (Each repstg 500 Preferred shares)
└─ 這張證券是 ADR（普通權益）      └─ 它「代表」特別股，但那不是它的種類
```

第一版沒有分開，於是 ITUB、AMX（América Móvil）、KOF（可口可樂 FEMSA）、BNS
這些大型 ADR 全被當成特別股或單位濾掉。同樣被誤判的還有：

- **合夥事業**（AllianceBernstein、Brookfield、Alliance Resource 等 49 檔）
  的權益就叫「Common Units」，不是 SPAC 認購單位
- **公司名稱裡的字**：「Our Bond, Inc. - Common Stock」被當成債券

這類錯誤**不會有錯誤訊息**——那檔只是從此不再出現，沒人會發現。因此每一個
修正過的案例都在 `tests/test_security_type.py` 釘住。

### 公司清單來源

| 來源 | 角色 | 提供內容 |
|---|---|---|
| NASDAQ Trader Symbol Directory | 主 | 交易所官方每日更新，含 Test Issue 與 ETF 旗標 |
| SEC `company_tickers.json` | 備援 | 含 CIK，但無交易所／ETF 旗標 |

- 交易所代碼會轉成 Yahoo Finance 格式：`BRK.B → BRK-B`、特別股 `BAC$B → BAC-PB`
- 檔尾的 `File Creation Time` 那行、以及 `Test Issue = Y` 的測試代碼都會濾掉
- 解析出的筆數若明顯過少（< 3000），**直接報錯而不覆蓋既有清單**，
  避免用殘缺資料把好的清單洗掉

### 帳本與重試

每一檔有四種狀態：

| 狀態 | 意義 |
|---|---|
| `pending` | 尚未嘗試 |
| `ok` | 成功 |
| `failed` | 失敗但仍可重試（`attempts < 3`）|
| `dead` | 已達重試上限，不再自動重試（需 `--reset-dead`）|

- **取件順序**：先做沒試過的，再做失敗次數少的。避免某幾檔一直卡在前面重試、
  讓其餘還沒試過的標的餓死。
- **「查得到但無分析師覆蓋」記為成功**，不是失敗——否則這類標的會每輪都被重試，
  永遠佔用配額卻不可能成功。判定依據是來源有沒有回應（`TargetQuote.responded`），
  不是比對錯誤訊息：某個來源自己壞掉時每一檔都會帶著它的錯誤，用字串比對會把
  大量「本來就沒人追蹤」的標的誤判成失敗。
- **來源層級的失敗不算這一檔的失敗**，狀態留在 `pending`、不累加 `attempts`，
  順延到下次執行。實測第一次跑 1500 檔時有 1190 檔敗在 Yahoo 限流；若照樣記成
  失敗，一次限流就會讓上千檔各消耗一次重試次數，三輪之後全數變成 `dead`——
  問題明明出在來源而不是這些標的。
- 每處理 200 檔就把帳本與結果落地一次，**執行中途被中斷不會白做**。
- 帳本刻意用 CSV 而非 SQLite：它要 commit 進 repo 才能跨執行保存進度，
  文字格式的 diff 看得懂、衝突也處理得了。

### 為什麼結果是分片 JSONL 而不是「一檔一個檔案」

8000+ 檔會產生 8000+ 個小檔，而價格每天都變，等於每天 commit 八千個檔案變更，
repo 會迅速膨脹。分片 JSONL 同樣是「一筆結果一筆記錄」、可逐筆讀寫更新，
但檔案數收斂到約 40 個，git diff 仍然看得懂。

### 排程

`.github/workflows/universe-crawl.yml`：每日 01:10 UTC 重建清單並開新一輪，
之後每 3 小時續跑一批。單次上限 1500 檔、job 上限 330 分鐘（低於 GitHub 的 360 分）。
`concurrency` 群組確保兩次執行不會同時寫帳本。

### 為什麼每日開新一輪不能用 `--keep-ok`

`--keep-ok` 會保留已成功的項目不重抓。用在「一輪中途補跑失敗的」是對的，
但當成**每日開新一輪**的預設就錯了：一檔成功之後永遠不會再被取用，
收盤價、目標價、每股淨值全部凍結在第一次抓到的那天——掃完一輪之後，
資料就再也不會更新了。

節流後全量約需 100 分鐘的請求時間，分散在每天多個班次裡綽綽有餘，
沒有理由為了省時間而讓資料停在過去。

### 為什麼 checkout 一定要指定 `ref: main`

`concurrency` 群組會讓後到的執行排隊。等輪到它時 main 早就被前一個執行推進了，
但 `actions/checkout` 預設取的是**觸發當下的 commit**——等於拿一份過期帳本開始跑，
跑完必然 rebase 衝突。2026-08 就是這樣丟掉一整批 1500 檔的進度。

### 衝突要用記錄層級合併，不能靠文字比對

爬一批要跑十幾分鐘到數小時，commit 失敗等於整批白做。而 `data/ledger.csv` 與
`data/results/*.jsonl` 都是**以 ticker 為鍵的記錄集合**，不是散文——衝突有唯一
正確解：取兩邊聯集，同一檔取較新的那筆（`scripts/resolve_crawl_conflict.py`）。
`<<<<<<< =======` 對這種檔案毫無意義，而放棄整批更是最糟的選擇。

合併後衍生檔（`universe_latest.json`）會**重新產生**而不是挑一方，否則儀表板
會與帳本對不上。真的遇到無法自動合併的檔案時，工作流程會保留現場並失敗，
不會靜悄悄地把資料丟掉。

## 儀表板設計

兩個模組共用 `docs/style.css`，採**北歐簡潔商務風格**：米白紙感表面、髮絲級分隔線、
以留白而非外框分區、輕量字重、小型大寫標籤、無陰影、近乎直角的圓角。

資料色則以**可辨識性優先**，不因風格而犧牲：北歐風常見的低彩度色調無法通過色盲辨識
檢驗，因此採用加深但仍偏沉穩的六色（fjord blue／rust／indigo／spruce／amber／heather），
並以 `dataviz` 的驗證腳本確認：

- 淺色模式：CVD 相鄰色差 ΔE 13.6、一般視覺 ΔE 23.4、彩度與亮度帶全數通過
- 深色模式：另行取階（非直接反轉），CVD ΔE 8.7、對比全數 ≥ 3:1

## 資料品質處理

- 抓不到目標價或收盤價的標的，`upside_pct` 為 `null`、信心等級標記「暫缺」，
  **不以任何方式填補**，並可在儀表板上選擇顯示或隱藏。
- 信心等級：分析師 ≥5 家且有 2 個來源 → 高；≥5 家但單一來源 → 中；<5 家 → 低。
- 目標價相對現價偏離超過 +300% / −90% 者標記為「疑似資料異常」（保留但註記，不剔除）。
- 維基百科的 `BRK.B` 等代號會轉成 Yahoo Finance 使用的 `BRK-B`，否則抓不到價格。

## 已知限制

1. **目標價不等於價值判斷**：上漲空間為正只代表分析師共識價高於現價，不代表便宜。
   分析師普遍存在偏多傾向，且目標價常在股價變動後才「事後」調整。
2. **股票池為 S&P 500**：不含中小型股與非成分股；成分股清單取自維基百科當前版本，
   屬 look-back bias（歷史回溯時成分股其實會變動）。
3. **Yahoo 未提供目標價的更新日期**，因此無法判斷某檔的共識價是否已數月未更新。
4. 本模組同樣在無對外網路的沙盒中開發，所有邏輯以合成資料測試
   （`tests/test_valuation.py`），真實網站回應格式尚待第一次正式執行後人工核對。

# 模組六：尾部脆弱度雙閘門

依《v3.0 模組四 — 尾部脆弱度雙閘門 · 接線說明》實作。**影子運行：只記錄、不下單。**

## 讀這個模組之前

接線說明第 0 節的三句話照抄，不打折：

- 期望值約 **+1.2%/年**，且大部分來自約七年一遇的危機型事件。
  它**不是黑天鵝防護罩，是薄利的尾部保險**。
- **慢閘的門檻未經真實資料校準。** 結構驗證過（久期污染、趨勢污染），閾值沒有。
- **快閘的統計基礎是 n=1。** 樣本裡真正的危機型事件只有 2020 一個。

因此儀表板把這三點放在頁面**最上方**，而不是頁尾小字。理由很簡單：一個紅色的
`STRESS` 看起來跟已驗證過的訊號一模一樣，使用者沒有辦法從畫面上分辨。

說明第 6 節第三步建議先影子運行三個月——儀表板天生就是那個形態，
所以本模組**不接任何下單邏輯**。

## 三條必須守住的規則，以及它們為什麼難守

三條規則的共同點：違反時**正常路徑全部通過**，錯誤只在真正需要這個模組的那天才顯現。
因此每一條都寫成程式碼裡擋得住的東西，不是註解。

| 規則 | 違反時的症狀 | 怎麼擋 |
|---|---|---|
| ① `base_alloc` 是唯一能加碼的來源 | **回測變好看了** | `_assert_veto_only()` 每次呼叫都檢查 |
| ② `state` 必須跨日持久化 | 快閘永遠不觸發，畫面一切正常 | `assert_state_consistent()` + workflow commit `data/tail/` |
| ③ 價格必須除息調整 | 慢閘長期偏紅，沒有人起疑 | 專用的 `fetch_adjusted_close()` |

**規則 ③ 有一個現成的陷阱。** 這個 repo 既有的 `sources/yahoo.fetch_yahoo_close()`
用的是 `auto_adjust=False`——沿用它會一路過關、不拋任何例外，只是慢閘從此長期偏紅。
兩個函式名字像、型別一樣、都能跑，差別只在一個布林參數，而那個參數決定這個模組
是不是在說謊。所以 `tail_gate/data.py` 另外寫了一個，而不是重用。

**規則 ② 是說明第 7 節點名的最常見失效模式。** `consec_inversion` 漏存，
計數器每天從 0 重數，倒掛連續一個月也到不了 `persist_days=4`。
測試 `test_forgetting_to_persist_state_silently_disables_the_fast_gate` 就是在演這件事：
連續 30 天倒掛，閘門完全沒有作用。

## 兩道閘門

**慢閘** 用 `CreditProxyGate`（說明第 2 節的建議）：HYG／LQD／IEF 全免費，
自 2007-04 起涵蓋 2008 與 2020。核心處理是**把久期洗掉**——利率大跌時 HYG 會漲，
但那不代表信用轉好；不對沖的話 2022 年的升息會被誤讀成信用惡化。

為什麼不用 HY OAS：那是 ICE 授權資料，而本專案**已經實測過** FRED 只給得出近三年
（見 `liquidity_monitor/sources/fred.py` 的診斷）。說明第 2 節那一行限制，
在這個 repo 是踩過的坑，不是理論。

**快閘** 三個類別各自獨立判定，數量決定否決等級：期限結構倒掛（VIX9D > VIX > VIX3M）、
波動的波動（VVIX 百分位）、信用急變（HY OAS 20 日變化）。

持續期閘門**只作用在期限結構那一項**。說明寫的是「曲線倒掛需連續 4 日才降級」，
不是整個快閘延後——信用急變是急性事件，等四天等於錯過。這個區別有實質後果，
所以有獨立測試守著。

`persist_days` 是**刻意放棄**一部分事件：說明第 8 節指出 Type II（踩踏型）的干預
EV ≈ 0，是最頻繁的事件類型卻無法獲利。把它調小會抓到更多事件，但抓到的多半是那一類
——看起來反應更快，實際上是在賠手續費。

## 期望值：參數是回推的，這件事必須講明白

說明只給了結論（1.2%／89%）與兩個可查的量（七年重現期、0.5~1.0 次/年的誤觸目標），
沒有給每一項假設。所以 `ev.py` 的預設值是**回推**出來的——先固定可查的量，
再解出剩下的，使模型重現說明的那兩個結論。

這不是獨立驗證。但另一種做法更糟：自己另編一組假設、算出 4%/年然後印在畫面上。
（第一版就是這樣，測試抓到了。）

**敏感度分析的結論相當刺耳**：假設的 `whipsaw_cost` 是 5.52%，損益兩平點約 **7.02%**
——誤觸成本只要比假設高約 **27%**，整個模組的期望值就歸零。而這個參數**完全沒有實測過**。

日誌因此存了 `tqqq_close` / `qqq_close`（說明第 5 節）：等快閘真的觸發並回場後，
就能算出實際的來回成本，把這個模組最大的不確定性換成一個量測值。

## 首次真實執行（Actions，2026-08-13）

資料全部取得，無失敗。VIX9D 11.09 < VIX 14.55 < VIX3M 18.53（正常正價差），
慢閘 `EXPANSION` 15.1 分，否決等級 0，配置未調整（主評分為 100% QQQ）。

**代理驗證（說明第 6 節第一步）跑出了一個要更正的東西。**

| 判讀項目 | 實測 | 門檻 | |
|---|---:|---:|---|
| 代理指數回撤 vs OAS 水準 | 0.7715 | > 0.60 | 達標 |
| 60 日變化的反向對應 | −0.9026 | < −0.50 | 達標 |
| 分級一致率（第一版） | 0.2865 | > 0.70 | 未達標 |

第三項看起來像代理失敗。**但那是量尺壞了。** 第一版拿代理的「絕對門檻分級」去比
OAS 的「四分位分級」，而四分位在結構上強制各 25%——平靜期裡它會把最近三年相對
最差的 25% 天標成 `STRESS`，那些日子的絕對壓力可能只有 3% 回撤，代理當然說
`EXPANSION`。

用**完美相關**（corr = 1.0）的合成序列驗證：第一版指標回 **0.2508**，與實測的
0.2865 幾乎一樣。**一個無論代理好壞都不會過關的指標，量不出任何東西。**

改為兩個指標，兩個都報：

- `regime_agreement_rank`——兩邊都取四分位，問「代理**排序**日子的方式跟 OAS 一樣嗎」。
  這才是說明第 6 節的「方向對不對」，0.70 的門檻套在這一個。
- `regime_agreement_absolute`——代理的正式門檻 vs OAS 四分位。**保留**它是因為
  「出貨用的門檻沒校準」這件事該有數字，不該被新指標蓋掉。

### 修好量尺之後：代理仍未達標，而門檻本身也有問題

換成公平的比較之後，實測是 **0.3953**，門檻 0.70。**修好量尺並沒有救回代理。**
（這是應該的——如果換個算法就通過了，那才要擔心自己在搬球門。）

但 0.3953 這個數字要放在基準旁邊才讀得懂。四分位一致率比相關係數難達標得多：

| 相關係數 | 雙變量常態下的期望四分位一致率 |
|---:|---:|
| 0.60（說明的門檻） | 0.429 |
| 0.772（實測） | 0.524 |
| **0.928** | **0.700（說明的一致率門檻）** |

兩個結論同時成立，缺一不可：

1. **說明的三個門檻彼此不相容。** 一致率 0.70 需要相關係數約 **0.93**，
   而說明自己的相關係數門檻只有 0.60（對應一致率僅約 0.43）。
   一個剛好通過前兩項的代理，**數學上不可能**通過第三項。
2. **代理本身也確實不足。** 實測 0.3953 低於它自己的相關係數所預測的 0.524，
   落差 −0.13。所以這不能全部推給門檻。

因此儀表板把三個數字並列：實測、該相關係數的期望值、以及門檻。
只報「0.395 vs 0.70」的話，讀者無從分辨是代理差、還是門檻本來就達不到。
（同一個模式在模組三用過：以純雜訊的期望 z 值當基準。）

**結論不變：慢閘門檻未經校準，不該接下單邏輯。** 說明第 6 節列的第一個補救手段
（「先調 `hedge_beta`：固定 vs 滾動」）在這份資料上等於沒有動作——實測滾動 beta
0.4667，與固定值 0.47 差 0.0033。真要補救得直接跳第二步（用 JNK 取代 HYG）。

## 回補歷史：把「沒有樣本」換成量測值

`scripts/backfill_tail_gate.py` + `.github/workflows/tail-backfill.yml`（手動觸發）。

**為什麼值得做**：這個模組最大的問題不是它會不會動，是 EV 模型五項假設全部沒有
實測過，而 `whipsaw_cost` 只要比假設高約 27% 就讓整個模組期望值歸零。模組一有
**十年的重建分數歷史**（`scores_history_reconstructed.csv`，2016 起 2513 個交易日），
價格類輸入也都有長歷史，所以回補可以把 `false_positive_per_year` 與 `whipsaw_cost`
兩項變成**量測值**——那正是說明第 5 節存收盤價的用意，也是第 6 節第二步。

### 唯一真正的風險是前視偏誤，而且它不會報錯

拿今天的完整序列去算 2018 年的壓力水準，`stress_level` 的 500 日高點會包含 2020 年
的崩盤——於是 2018 年的每一天看起來都「離高點很遠」，**回測會變得非常漂亮**。

規則只有一條，沒有例外：**每一天都先把所有序列切到當天為止，再交給閘門。**
閘門本身完全不知道自己在回測——它拿到的東西跟正式執行時一模一樣。這也是為什麼
回補直接呼叫 `TailFragilityGate.apply()`，而不是另寫一份「回測版」邏輯：
另寫一份，兩邊就會慢慢長歪。

測試方式是**注入未來**：同一段歷史跑兩次，一次乾淨、一次在尾端注入崩盤，
崩盤日之前的每一列輸出必須逐欄相同。已用變異測試確認這則測試真的會咬——
把切片改成回傳整條序列後，它立刻失敗。

### 三個必須寫在報告裡的偏差

1. **`base_alloc` 是重建的，且未套用 Gate A/B/C 上限。** 分數歷史只存了
   `composite_score`，所以只能走部位階梯。實際部位只會更保守，因此回補的
   base_alloc **偏積極**，模組六可砍的空間偏大。
2. **HY OAS 只有近三年**（ICE 授權）。更早期間「信用急變」這一類別沒有輸入，
   快閘在那段時間最多只有兩類可觸發。
3. **回補列標為 `source=backfill`**，與 `live` 分開計數。混進日誌而不標，
   畫面上會看起來像已經影子運行了十年——但那是重建的，不是觀測到的。

歷史長度不足的日子（慢閘需要 500 日回撤與 250 日百分位）**跳過**，不給數字：
那種日子算出來的不是壓力，是「歷史還不夠長」。

### 首次回補實測（2016-08-12 → 2026-08-12，2511 個交易日）

**結論：以實測參數，這個模組每年淨 −4.1%。** 說明估的是 +1.2%。

| | 原假設 | 回補量測 |
|---|---:|---:|
| 誤觸次數／年 | 0.80 | **14.20** |
| 每次誤觸的來回成本 | 5.52% | 0.687% |
| 年化誤觸成本 | 4.42% | **9.76%** |
| **年化期望值** | **+1.20%** | **−4.14%** |

處於否決狀態的日數佔 26.4%——那不是「尾部保險」，那是一個常態開著的濾網。

#### 回補當場抓到兩個我自己的錯

**① 符號寫反，而且它讓結論整個顛倒。** `measure_whipsaw()` 算的是
「TQQQ 倍數 − QQQ 倍數」，欄位卻叫 `avoided`（避開的損失），下游又取了負號。
但否決期間**並沒有持有 TQQQ**，所以 TQQQ 跑贏是**錯過的漲幅、是成本**。

實測 142 次進出平均 **+0.687%**，被報成 −0.687%——正負一顛倒，這個模組就從
「每年倒賠 4%」變成「免費的保險」。最刺眼的一次是 2026-07-29：一天之內
TQQQ +9.6%、QQQ +3.3%，閘門讓你整段錯過，卻被記成效益。
欄位已改名為 `tqqq_minus_qqq`，並補上兩則方向相反的測試。

**② VVIX 門檻在結構上就是壞的。** 拆開三個類別看：

| 類別 | 觸發日數 |
|---|---:|
| 期限結構倒掛（且達 persist 4 日） | 66 |
| **波動的波動（VVIX 百分位 ≥ 80）** | **568** |
| 信用急變（HY 20 日 ≥ 75bp） | 14（HY OAS 僅涵蓋 731 日） |

對**滾動 250 日百分位**設固定門檻，觸發率在數學上就被釘死在 (100−門檻)%：

| 門檻 | 實測觸發率 | 結構上必然 |
|---:|---:|---:|
| ≥ 80 | 22.6% | ~20% |
| ≥ 95 | 5.5% | ~5% |
| ≥ 99 | 1.5% | ~1% |

門檻 80 就是 20% 的日子，**無論市場平靜或動盪都一樣**。它完全不帶「現在是否
異常」的資訊——相對過去 250 天的前 20%，永遠有 20% 的日子。這與校準那次踩到的
是同一類錯誤：一個觸發率被結構釘死的指標，量不出東西。

**這一項是本專案自己訂的**（說明沒有給 VVIX 與 HY 的具體數值），所以是實作的
問題，不是說明的問題。

**沒有把門檻調到剛好命中 0.5~1.0 次/年的目標**——那是拿目標去配參數，正是說明
第 0 節說「未經校準」的那件事，調完只會讓它看起來校準過。門檻維持原狀，
把觸發率與結構性缺陷一起呈現在畫面上。

### 量測結果怎麼用

儀表板把「原假設」與「回補量測」並列，**不自動改寫假設**。回補是重建而非觀測，
把它當成已驗證會言過其實。並列呈現，讓差距自己說話。

# 模組七：類股主要 ETF 趨勢

`sector_trend/` + `docs/trend.html`。每個交易日收盤後執行。

## 與模組四的分工（先講清楚，否則兩頁看起來像同一件事）

| | 模組四 | 模組七 |
|---|---|---|
| 視窗 | 1 日～3 月 | 1 月～3 年 |
| ETF | 每類股一檔（11 檔 SPDR） | 每類股多檔（SPDR／Vanguard／iShares）＋產業型 |
| 看什麼 | 相對強弱象限、資金流 | 均線位置、距 52 週高低、趨勢路徑 |
| 價格 | 未調整 | **除息調整** |
| 回答 | 資金正在往哪一格走 | 這個類股在什麼趨勢裡，換一檔 ETF 結果會不會不一樣 |

兩頁的類股代表 ETF **刻意相同**（XLK 代表科技，兩邊一致），有測試守著——
各用不同 ETF 代表同一類股的話，同一天會顯示不同的漲跌，而讀者沒辦法知道
是哪一邊的問題。

## 除息調整為什麼在這裡是必要的

公用事業與必需消費的殖利率約 3%，資訊科技不到 1%。用未調整價比較**一年以上**
的報酬，等於系統性低估防禦類股約兩個百分點——而畫面上完全看不出來，只會得出
「防禦類股長期就是比較弱」這種被股利吃掉的結論。

模組四最長只看三個月，未調整價的影響有限，所以沒有改它。**兩頁的短期數字會
有些微差異，這是預期中的，不是其中一邊算錯。**

## 多檔 ETF 是重點，不是重複

「科技類股今年漲多少」其實取決於你拿哪一檔：XLK 只取 S&P 500 成分，VGT 是
MSCI 美國 IMI（含中小型），IYW 追羅素 1000。追的指數不同，成分與權重就不同。

因此每個類股列出多檔，並算出**同類股、不同發行商的一年報酬離散度**。

### 第一版把兩件事混在一起量了（首次真實執行抓到）

原本的離散度把次產業 ETF 也算進來，實測結果看起來很驚人：

| 類股 | 第一版報的 | 真正的（只看全類股 ETF） | 差額來自 |
|---|---:|---:|---|
| 醫療保健 | 50.7pp | **1.55pp** | XBI 生技 +81% |
| 原物料 | 29.1pp | **0.23pp** | XME 金屬礦業 +48% |
| 金融 | 21.3pp | **2.97pp** | KRE 區域銀行 +34% |

**沒有人會拿 XBI 代表醫療保健類股。** 把它算進「同類股離散度」，那個數字就在
回答一個沒有人問的問題，而標籤卻說它在回答「選哪一檔會不會不一樣」。

修正後每檔 ETF 標上 `broad`（追整個類股）或 `industry`（次產業），離散度**只計入
`broad`**，次產業標的在畫面上另外標示。

真正的結論反而相反：**全類股 ETF 之間相當一致（0.2～4.5pp），最大的是資訊科技
的 4.51pp**——因為 VGT 含中小型、IYW 追羅素 1000，指數定義確實不同。

## 沒有自創的綜合分數

呈現的是均線位置、距 52 週高低點、各視窗報酬，全部可以自己驗算。
不做「趨勢強度 0-100」那種東西——那需要校準，而這個專案已經有前車之鑑
（模組六的 VVIX 門檻：對滾動百分位設固定門檻，觸發率在數學上被釘死）。

50/200 日均線是市場慣用的長度，不是本專案挑的。挑一組「回測最好看」的均線長度
就是在配參數。

## 其他刻意的選擇

- **廣度用固定的代表 ETF 計算。** 把所有 ETF 都算進去的話，「11 檔裡有幾檔站上
  200 日線」會隨我今天列了幾檔科技 ETF 而變動——那不是廣度，是取樣。
- **資料基準是收盤日，不是執行日。** 週末或同日重跑時用執行日，會讓歷史多出
  一筆其實是同一個收盤的紀錄（模組四踩過這個坑）。
- **不足 200 天就不算 200 日均線**，回報「歷史不足」。算出來的不是趨勢，
  是「歷史還不夠長」。
- **抓不到的 ETF 會列在畫面上**，不會靜靜從表格消失。

## 儀表板的介面規則

七頁共用 `docs/style.css` 與 `docs/ui.js`。以下不是「好不好看」的主觀調整，
是**量測出來的問題**對應的修正。

### 導覽列固定在頂端

七頁高度實測 3,600～20,000px（估值表最長）。導覽若跟著捲走，換一個模組就得先
捲回最上面。固定住之後必須自己畫底色，否則內容會從底下透出來。

### 手機用短名，單行橫向捲動

實測手機（390px）導覽高達 **144px** 且最後一項被切掉：七個完整名稱各只分到約
40px，「模組一：市場流動性監控」被拆成**一行一個字**。改為短名（`① 流動性`）
加單行捲動後降到 **50px**，七項全部可達。

全名與短名都在 DOM 裡、以 `display` 切換——用 `font-size: 0` 之類的技巧會讓
螢幕閱讀器把兩份都念出來。

### 模組選單

標籤列適合「快速切換 + 看出我在哪一頁」，但它有兩個說不出口的東西：
每一頁**在做什麼**（「模組三：策略回測」回測了什麼、用什麼資料？），
以及手機上排在後面的模組——那條列是橫向捲動的，可能從來沒被發現。

選單補這兩件事：每項一句話說明、一次看得到全部七項。

**依模組編號 1→7 排列。** 第一版按主題分組（市場狀態／類股／個股／策略），
結果編號被打散成 1,5 / 4,7 / 2 / 3,6——分組本身有它的道理，但代價是使用者記得的
「模組三」在畫面上要用找的。編號是這個專案對外的固定稱呼，順序就該照它。

順序不在選單裡另外排，而是**沿用 nav 的順序**；`nav` 是否為 1→7 由測試守著，
在兩個地方各排一次就等於多一個會走鐘的來源。多欄版面用 `grid-auto-flow: row`，
閱讀順序是「先左右、後上下」，因此仍然是 1234／567。

**由既有的 nav 連結生成，不是另外寫一份。** 七頁的導覽列已經有測試守著彼此
一致，再手寫一份選單連結就等於多一個會走鐘的來源。只有分組與說明文字集中在
`ui.js` 的 `MODULE_INFO`，有測試檢查每一頁都有條目、每個分組都宣告過。

- 桌機：標籤列保留（切換快），選單作為「看全貌」的輔助
- 手機：標籤列收起，只留一顆顯示目前頁面的按鈕——橫向捲動會藏東西，選單不會
- 無 JS：按鈕根本不會被建立，隱藏標籤列的 CSS 掛在 `.menu-toggle ~` 之後，
  因此不生效，導覽維持原樣（已實測：停用 JS 時全部連結仍在）
- 鍵盤與輔助技術：`aria-expanded` / `aria-controls` / `aria-current`，
  Esc 與點擊外部都能關閉

### 表頭跟隨捲動，但只在放得下的時候

估值表在桌機上約 20,000px 高，捲到中段時滿螢幕都是**沒有欄位標題的數字**，
`175.58` 是收盤價還是目標價完全看不出來。

但這件事不能無條件開啟：`.table-scroll` 用 `overflow-x: auto`，而 CSS 規定另一軸
的 `visible` 會被強制成 `auto`——那個容器因此變成捲動盒，把 `position: sticky`
綁在裡面。**實測捲動 4000px 後表頭的 top 是 −2745，完全沒有黏住。**

所以「橫向捲動」與「表頭跟隨」無法並存，得看該表格在當下寬度**到底有沒有溢出**。
那是可以量的，不必用斷點猜：`ui.js` 逐一比對 `scrollWidth` 與 `clientWidth`，
放得下就開啟表頭跟隨，放不下就維持橫向捲動。resize 與表格填資料後都會重算。

實測既有頁面裡只有估值表會溢出（1280px 下 8px），把它的右內距從 14px 收到 10px
就放得下了。手機上估值表與趨勢表仍需橫向捲動，因此不套用表頭跟隨——這是
預期中的降級，不是失效。

# 模組八：尿布單價監控（M 號）

## 這個模組在回答什麼問題

跟模組一到七完全不同的性質——不是美股，是消費採購。監控尿布 M 號在三個
品牌／通路的每日最低單片價格：**滿意寶寶日本境內版**、**Aiwibi**、**奢寵幫**。
三者彼此不是同一件商品的不同賣場，價格高低本來就不該放在一起比大小，
每個品牌只跟自己的近期價格比。

## 核心邏輯

1. **當日最便宜單片價**：同一天同一品牌可能有多個平台的報價，取單片價
   （= 包裝售價 ÷ 片數）最低的一筆作為當日代表值。用最低價而非平均價，
   是因為使用者實際能拿到的價格就是各平台裡最便宜的那個，用平均會把
   「其實有更便宜的選擇」這件事平均掉。
2. **近期平均**：前 14 天（不含當天）的「當日最便宜單價」平均值，作為比較基準。
   14 天是折衷值——太短容易被單一天的異常報價牽著走，太長則會把一個月前的
   價格也當成「近期」；非回測校準的數字。
3. **顯著下跌**：今日最便宜單價跌破近期平均 20% 以上時標示。歷史點數不足 5 筆
   （剛上線、或某幾天忘記填資料）時不判定，避免用一兩筆資料誤判。

以上三個數字（視窗天數、最少樣本數、跌幅門檻）定義在 `diaper_monitor/config.py`。

## 資料來源：人工填寫，不是自動爬蟲

蝦皮、momo、PChome 等平台對非登入的自動化請求普遍有防爬機制，貿然爬取容易
撞到服務條款；就算能爬到，頁面改版時爬蟲最危險的失敗方式不是報錯，是
**安靜地**抓到過期或錯誤的價格，而錯誤的資料會直接誤導「顯著下跌」的判定。

比照模組一 `manual_overrides.json` 的前例：每日查價後填入
`data/diaper_monitor/manual_prices.csv`，欄位格式與範例見同資料夾的
`README.md`。之後若要接自動化來源，建議在 `diaper_monitor/sources/`
底下新增個別平台的擷取模組，輸出與這份 CSV 相同的欄位即可，
`pipeline.py` 不需要更動。

## 架構

```
diaper_monitor/
  config.py    品牌清單、比較視窗、門檻
  pipeline.py  讀報價 -> 換算單片價 -> 取當日最便宜 -> 與近期平均比較
  storage.py   寫 docs/data/diaper/latest.json、建立報價表範本
data/diaper_monitor/
  manual_prices.csv  每日人工填入的報價（唯一資料輸入）
  history.csv        每日執行後累積的「當日最便宜單價」序列，近期平均由此計算
docs/diaper.html, docs/diaper.js   儀表板（模組八）
scripts/run_diaper_monitor.py     每日執行入口
.github/workflows/diaper-monitor.yml  在 manual_prices.csv 有更動時執行，
                                       並每日排程一次作為備援
```

## 使用方式

```bash
python3 scripts/run_diaper_monitor.py -v
python3 scripts/run_diaper_monitor.py --as-of 2026-08-14
```

## 免責聲明

本專案為上述兩份分析框架的機械化資料爬取與計算實作，**產出結果非投資建議**，
開發者非持牌投資顧問。

模組一無法預警外生衝擊型事件（如疫情、地緣戰爭）；槓桿ETF(TQQQ)具每日重設特性，
長期持有於震盪盤中會產生顯著損耗。使用前請詳閱文件本身第285-292行之誠實原則與
本README之已知限制。

模組二呈現的是分析師共識目標價與市價的差距，**不構成任何個股的買賣建議**；
目標價的準確度沒有保證，且不同分析師的評估基礎與時間範圍可能差異很大。

模組六是**影子運行**：慢閘門檻未經真實資料校準，快閘的危機型事件樣本 n=1，
期望值模型的五項假設全部未實測。在跑完接線說明第 6 節的驗證之前，
它的輸出不該接上任何下單邏輯。

模組八呈現的是**人工填入**的每日報價換算結果，非即時自動抓取；資料的正確性
取決於填寫當下有沒有查對品牌、尺寸與片數，**下單前請以各平台當下頁面實際
顯示的價格為準**。「顯著下跌」的 20% 門檻與 14 天比較視窗是折衷設定，
不是回測校準過的最佳參數。

模組九是機構共識目標價與市價落差的**再篩選**，不是新的資料來源；目標價本身
的所有限制（分析師偏多傾向、共識價事後調整、逐機構資料未啟用）同樣適用。
分歧度分層是相對候選股池本身分布算出來的，隨每次快照的股票池變動而變動，
不是一組固定不變的百分比。

# 模組九：買評缺口雷達

## 這個模組在回答什麼問題

模組二（分析師估值比較）每天產出全部 503 檔 S&P 500 成分股的目標價與市價
比較，但表格本身沒有回答一個常見問題：「在機構喊買的股票裡，現價跟目標價
差最多的是哪幾檔？這份樂觀共識有多少人不同意？」模組九從模組二的當日報告
篩出獲「買入」或「強力買入」評等的股票，取上漲空間最大的前 10 名，並用
目標價分歧度——同一檔股票裡最樂觀與最保守的機構目標價差多遠——衡量這份
共識背後藏了多少分歧。

## 核心邏輯

1. **候選股池**：評等為 `buy` 或 `strong_buy`、上漲空間與分歧度都算得出來、
   未被模組二標記為異常（`implausible`）的股票。
2. **排序**：候選股池依上漲空間（現價 → 共識目標價）由大到小排序，取前 10。
3. **風險分層**：把每檔的分歧度拿去跟**同一次候選股池自身的分布**比較——
   高於池內前 10% 為「極端」、前 25% 為「高」、高於中位數為「中」，其餘為
   「低」。門檻不是寫死的絕對數字，因為分歧度「算不算高」本來就取決於當下
   一整批買評股彼此的差異，而不是某個固定百分比。
4. **較上次比較**：每次快照都會跟上一次快照比對同一檔股票的名次，標出
   進步、退步或新進榜——這是唯一需要跨快照累積歷史的地方。

## 為什麼獨立成一個模組，而不是加在模組二的表格裡

模組二的表格是「全樣本瀏覽器」，每天重新整理、可自由篩選排序；模組九是
「每週一次的精選清單」，重點是**穩定**——同一份榜單放一整週，才看得出
「這檔股票已經連續三週在榜上」這種訊號。兩者更新頻率不同、目的也不同
（瀏覽 vs. 精選），硬塞進同一頁只會讓兩種需求互相干擾。

## 架構

```
gap_radar/
  pipeline.py   讀模組二的 latest.json -> 篩買評 -> 取上漲空間前N名 -> 風險分層
  storage.py    寫 docs/data/gap_radar/latest.json，並記錄每次快照的名次以算變化
docs/gap_radar.html, docs/gap_radar.js   儀表板（模組九）
scripts/run_gap_radar.py                 執行入口
.github/workflows/gap-radar.yml          每週排程一次（模組二排程之後）
```

## 使用方式

```bash
# 前提：docs/data/valuation/latest.json 已存在（先跑過模組二）
python3 scripts/run_gap_radar.py -v
```
